# 12月の忘年会に向けた設計案

2026-10-28 時点の実装を前提とする。以下の型・API・イベント追加は提案であり、未実装。
12月は「運営画面の統合」「キー入力式の物理ボタン」「結果を変えない演出」を優先する。
カード引き直しは余力枠、進行中の交換と効果付き特殊球は本番後を推奨する。

## 現状と見積もりの前提

- `openapi.yaml` は通常数字球のみを扱う契約。`PickedBall` は 1〜75 の整数。
- `backend/internal/model/room.go` の状態は waiting / playing / finished。
- 抽選状態は idle / picking / exhausted。抽選開始時には結果を決めない。
- `RoomService.finishPick` が未抽選数字から選び、カード・記録をまとめて保存する。
- カードは参加時でなく `RoomService.startGame` で全員分を生成する。
- `Card` は ID・36桁のカード番号・所有者・25マスを持ち、中央は FREE。
- `BingoRecord` はユーザー・ライン・順序、`ReachRecord` は初回リーチを記録する。
- 現在の記録にはカード版や、原因となった抽選 ID がない。
- `RoomSettings` は名前・説明・管理者。API 側の名称は `GameSettings`。
- 設定更新は waiting / playing で可能。新しい競技ルールは開始後に固定したい。
- `RoomService.mutate` はルームロック → DB transaction → commit → イベント配信。
- ロックは配信完了まで保持し、イベント送信失敗はログに残す。
- 更新系は `FindByIDForUpdate` で集約を読み、`Save` で子データも保存する。
- repository はカード・球・記録などを置き換える構造。履歴追加時は消失防止が必要。
- WebSocket は participant / display の2モード。運営画面も display 接続を使う。
- participant には自分のカード、display にはカードを含めない。
- `Initialized` が復帰時の状態を渡す。新機能もここから復元できる設計にする。
- `Settings.vue` は設定編集、`Controller.vue` は抽選・終了・QR操作。
- `Display.vue` は投影・球履歴・チャット・全画面・音声有効化を担当する。
- `Participant.vue` は待機表示・自分のカード・チャット・ビンゴ花火を担当する。
- `/` の部屋一覧、`/new` の部屋作成は今回の統合対象外。

工数は既存構造を理解した1人の実装・レビュー・動作確認の概算。
S＝1〜2人日、M＝3〜5人日、L＝6〜10人日以上。機材調達・会場確認は別途。
複数案の工数は単純加算せず、共通基盤と結合確認を含めて再見積もりする。

## 1. カード交換・引き直し

### 概要

「自分のカードを再生成する」と「他人のカードを受け取る」は別ルールとして扱う。
最初は抽選結果を知る前の引き直しだけに絞る。

| 案 | 条件 | 公平性・運用 | 工数 | 12月 |
| --- | --- | --- | --- | --- |
| A：待機中の引き直し | waiting 中、各人1回 | 全員同条件、開始後固定 | M | 余力があれば |
| B：初球前の引き直し | playing / idle、球履歴0、各人1回 | 配布時期は維持できるが開始直後に混雑 | M | Aの代替 |
| C：合意による交換 | playing / idle、双方1回、未ビンゴ | 戦略性が強く、談合・通信差への説明が必要 | L | 見送り |
| D：司会の一斉交換タイム | 抽選を止め、全員同じ受付時間 | Cより案内しやすいが進行が延びる | L | 次回検討 |

A と B は同時採用しない。引き直し後に元へ戻す・複数候補から選ぶ機能は付けない。
C は同一ルーム内の参加者同士のみ。ルーム間交換は対象外。

### ユーザー体験

- Aでは参加直後にカードを見せ、「1回だけ引き直す」を表示する。
- 確認文は「元のカードには戻せません。ゲーム開始後は変更できません」。
- 成功後は新カードと「引き直し済み」を表示。再読込しても回数は復活しない。
- 司会画面には参加人数と引き直し済み人数を表示し、待機中の案内に使う。
- 開始が先に確定した場合は「ゲームが始まったため変更できません」と再同期する。
- Cでは相手を選び申請し、相手が承認して初めて双方のカードを同時に交換する。
- 相手のカード全体の事前閲覧は提供しない。ただし口頭相談による有利交換は防げない。
- 申請には30秒の有効期限を設け、辞退・取消・期限切れを明示する。
- 承認待ちの間は抽選を止めず、次の抽選開始時に未承認申請を失効させる。

### データ/API 変更案

Aは参加時のカード生成が必要。現在の `startGame` の全件再生成を変更する。
既存 waiting 部屋のカード未生成分も、参加済みユーザーの再参加などで補完する。
開始時にも不足分だけ生成し、引き直し済みカードを上書きしない。

- `RoomSettings.cardPolicy`: `none | waiting_reroll | before_first_pick_reroll | swap`。
- ルールは waiting 中のみ変更可能。回数は初版では1固定でよい。
- `Card.version` と `Participant.currentCardId` を導入する。
- 版はユーザーへの割当変更ごとに単調増加させる。古い要求を見分けるために使う。
- 引き直しは新しい CardID を発行。カード番号も再生成する。
- `card_versions` に旧カードの25マスと割当履歴を保存し、旧版は現役から外す。
- `card_change_records` に roomId、操作ID、種類、当事者、変更前後のID・版、時刻を保存。
- `(roomId, actorUserId, requestId)` を一意にし、再送は保存済み結果を返す。
- 引き直し回数は保存済み成功記録から判定する。クライアント値を信用しない。
- Cの `card_exchange_requests` は双方のID・期待版・期限・状態を保持する。
- Cは数字配置と開いた状態を一緒に移す。所有者だけの書換えで履歴を失わないこと。
- 将来の記録は `BingoRecord` / `ReachRecord` に cardId・cardVersion・triggerId を追加する。

API は `/api/rooms/{roomId}` 配下の提案。

| 操作 | エンドポイント | 主な入力 |
| --- | --- | --- |
| 引き直し | `POST /cards/me/reroll` | requestId、expectedVersion |
| 交換申請 | `POST /card-exchanges` | requestId、targetUserId、双方の期待版 |
| 承認 | `POST /card-exchanges/{id}/accept` | requestId、expectedVersion |
| 辞退・取消 | `POST /card-exchanges/{id}/cancel` | requestId |

- 実行者は認証情報から決定。対象ユーザーを指定して他人の引き直しはできない。
- 403：権限不足、409：状態・版・残回数の競合、400：自己交換など不正入力。
- `CardReplaced` は本人だけに新カード・版・残回数を通知する。
- `CardExchangeRequested/Resolved` は当事者に通知。全体には必要なら件数だけを送る。
- `Initialized` に本人の現役カード・版・残回数・有効な申請を追加する。
- display や他の参加者へ新旧カードの数字配列を送らない。

### 境界条件・ロックとトランザクション

1. `mutate(roomId)` 内で `FindByIDForUpdate` し、権限・状態・版・残回数を再確認する。
2. 新カード生成、現役割当、履歴、回数消費、申請状態を同じ transaction で保存する。
3. commit 後に `queueParticipantEvent` の通知を配信する。失敗時は再接続で復元する。
4. 交換はルーム1個のロックで双方を更新し、片側だけ成功させない。
5. 承認待ち中はロックも transaction も保持しない。期限は承認時にサーバー時刻で判定する。

- picking 中の引き直し・交換承認は禁止。UI無効化に加えサーバーで拒否する。
- 抽選開始と承認の競合は、先にロックを得た処理の確定状態で判定する。
- ビンゴ達成者はCの双方とも対象外。獲得済みの賞・順位は移転させない。
- リーチ記録は現状「ユーザーの初回」という意味。Cでは履歴と現在状態を分ける。
- 交換後の現在リーチはカードから再計算し、過去の初回通知は消さない。
- 交換自体でビンゴを新規付与しない。既存ビンゴカードも対象外なので再受賞を防げる。
- 多重タブ・相互申請・複数相手への申請は、当事者ごと有効申請1件に制限する。
- finished への遷移で未決申請は失効。切断しても成功済み操作を戻さない。
- `Save` のカード置換で旧版・履歴が消えないよう、履歴を別保存するか集約に含める。
- プロセス内ロックだけでは複数インスタンスを保護できない。DB行ロックも維持する。
- 配信失敗でDBは巻き戻らない。requestIdで再取得し、再操作による二重消費を避ける。

### 実装ステップ（小さく分割）

1. AかBの片方を決め、ドメインの許可条件と同時開始時の期待結果を固定する。
2. 版・履歴・成功操作の一意制約を追加し、既存カードをversion=1として移行する。
3. Aなら参加時配布・不足分補完・開始時の既存カード保持を実装する。
4. 引き直しサービスとAPIを追加し、連打・開始競合・保存失敗を検証する。
5. participant の確認UIと待機中カード表示、Initialized復元を追加する。
6. 実機で再接続・多重タブを確認。Cは独立した後続案件にする。

### リスク・工数感・12月の推奨

A/BはM。カード生成時期・保存・通信・待機UIまで変わるため、小さなボタン追加ではない。
C/DはL。順位・リーチ履歴の意味と当事者合意まで扱う必要がある。
12月はAを余力枠とし、11月中旬までに競合試験が終わらなければ既存配布を使う。

## 2. 特殊球

### 概要

演出だけの球と、勝敗を変える球を分けて導入する。
12月は「ボーナス演出」を推奨し、効果付きルールは事前体験会を条件にする。

| 案 | 効果 | 工数 | 12月 |
| --- | --- | --- | --- |
| ボーナス演出 | 通常数字確定時に紙吹雪・短い音。開く条件は通常通り | S | 推奨 |
| ラッキーボール | 全員の閉じたマスをサーバーがランダムに2つ開く | L | 原則見送り |
| ワイルド | 全員が閉じた1マスを選んで開ける | L | 見送り |

ラッキーの「2マス」は各参加者のカードで2マス。数字2個を全体に引く案とは区別する。
閉じたマスが1つなら1つ、0なら効果なし。FREE・開済み・reach・bingoマスは対象外。

### ユーザー体験

- ボーナス演出は確定した数字を必ず読める状態にし、2秒程度で通常表示へ戻す。
- ラッキーは投影に「全員、ランダムで最大2マスOPEN」と表示する。
- participant は実際に開いたマスだけを強調し、通常数字による開放と区別する。
- ワイルドは参加者画面で選択→確認。司会画面には未確定人数と残り時間を出す。
- 例として20秒の共通期限を設け、未操作者はサーバーがランダム選択する。
- 選択受付中は次の抽選を禁止。切断した参加者にも期限時の自動選択を適用する。
- 選択速度で賞が決まらないよう、全員分を一括確定してからビンゴを発表する。
- 音なし・動きを減らす設定でも、種類と効果を文字・アイコンで伝える。

### データ/API 変更案

演出だけなら `PickedBall` の整数契約を維持できる。
`PickFinished` に任意の `presentation: { kind: bonus }` を追加する案が最小。
例：確定した通常数字の10球目・20球目に演出する。表示側で再抽選しない。

効果付き特殊球は数字配列への0・76などの混入で表現しない。

- ドメインの `PickedBall` を `{ id, sequence, kind, number?, resolvedAt }` にする。
- kind は `number | lucky | wild`。number は通常球だけ必須。
- `Room.PickedBalls []BallNumber` を抽選履歴へ拡張し、通常数字集合はそこから導出する。
- `DrawableNumbers` / `AllPicked` は通常数字75個の消費で判定する。
- 特殊球は通常数字を消費しない。数字が尽きたら新しい特殊球も引かない。
- `RoomSettings.specialBalls` に enabled、luckyWeight、wildWeight、numberWeight、maxSpecials。
- 初期値は無効、特殊球上限2回。確率は重み合計に対する比率として表示する。
- 上限到達時は特殊球の重みを0にし、残った通常数字を一様抽選する。
- 種類・対象マスの乱数はサーバーで決め、確定結果を保存してから通知する。
- ワイルド用に `pending_effects` と `effect_choices` を保存する。
- choice は effectId、userId、cardId、cardVersion、cellIndex、選択元、確定時刻を保持。
- `(effectId, userId)` の一意制約とrequestIdで再送を安全にする。
- 効果確定までは履歴をpendingとして管理し、resolvedAtは最終確定時に設定する。
- `BingoRecord` にtriggerIdを持たせ、どの効果で達成したか追えるようにする。

追加API案：`POST /api/rooms/{roomId}/effects/{effectId}/choice`。
入力はrequestId・cardVersion・cellIndex。本人の未確定選択だけを受け付ける。

- 通常抽選は既存の `/control/pick/start|finish|cancel` を維持する。
- 即時確定のluckyは `PickFinished` にkind・本人のカード差分を含める。
- wildは `SpecialEffectStarted` → `SpecialEffectResolved` の順で通知する。
- 最終の `PickFinished` は効果確定後に送る。開始だけでビンゴを通知しない。
- `Initialized` に効果ID・期限・本人の選択状況を含め、再接続から選べるようにする。
- display向けには選択人数・効果概要だけを送り、個人カードや選択マスは送らない。
- 球の型変更は破壊的。OpenAPI、Go生成型、Vue型・store・球一覧を同時に更新する。
- 旧整数履歴はkind=numberに移行。時刻不明の旧履歴に架空の抽選時刻を入れない。

### 公平性・ロック・例外

- 特殊球は全員対象とし、司会が受益者や有利なマスを指定できないようにする。
- 開始前に確率・上限・期限・自動選択・賞の扱いをルール画面と司会説明で共有する。
- 進行中は確率設定を変更不可。通常数字の残数でも見かけの発生頻度が変わる点を説明する。
- 特殊球の上限と通常球の終了条件を固定し、長引く進行を防ぐ。
- luckyは全員分の開放・リーチ・ビンゴ・球履歴を `mutate` の1 transactionで確定する。
- wildの待ち時間中はロックしない。選択保存と一括解決をそれぞれ短い `mutate` にする。
- 期限処理は永続化済みpendingを走査できる形にし、サーバー再起動後も解決する。
- 効果解決・二重タイマー・ゲーム終了の競合をDB状態と一意制約で防ぐ。
- ゲーム終了時は未解決wildを取消し、未適用マスを開かず、取消イベントを先に送る。
- pending中のカード交換は禁止。期待版の不一致もサーバーで拒否する。
- 同じマスが後の通常数字で当たっても再度開放・受賞しない。
- 同一効果内の複数ビンゴは、受付順でなく同着扱いを推奨する。
- 現状のBingoOrder・ActivityLogの順位算出は同着を直接表現しないため改修が必要。
- 賞品枠を超える同着は別抽選など、会場運用まで開始前に決める。

### 実装ステップ（小さく分割）

1. まず結果不変のボーナス演出を追加し、表示・音・再接続時の再演出抑制を確認する。
2. 効果付き版はルールを固定し、球オブジェクトと通常数字集合への移行を行う。
3. セル開放と記録計算を共通化し、通常数字の結果が変わらないことを確認する。
4. luckyだけ実装し、残り0/1/2マス・複数ライン・75球終了を検証する。
5. wildの永続pending、期限処理、選択API、全員確定を追加する。
6. 同着・再起動・切断・終了競合を試し、ルール説明込みの体験会を行う。

### リスク・工数感・12月の推奨

演出はS、luckyはL、wild追加もL。順位の納得感と復帰処理が主なリスク。
12月はボーナス演出のみ推奨。効果付き特殊球は実験用ルームで試す範囲に留める。

## 3. 4画面の整理

### 概要

settingsとcontrollerを「運営コンソール」にまとめ、基本は3用途に整理する。
参加者の個人端末、会場の投影、運営の端末という役割は維持する。

### ユーザー体験

- 運営コンソールに「進行」「設定」のタブ。入室時は進行を開く。
- 上部にルーム名・参加人数・ゲーム状態・接続状態を常時表示する。
- 進行タブは大きな抽選ボタン、キャンセル、QR、投影を開くリンクを置く。
- ゲーム開始・ゲーム終了の確認は残す。抽選終了とゲーム終了を明確に分ける。
- 設定タブでは基本情報・管理者を編集し、開始後の競技ルールは固定表示にする。
- 別案としてdisplayに管理者用操作オーバーレイを付ければ、1台でも進行できる。
- オーバーレイは明示的な「操作を有効化」で開始し、状態バッジを表示する。
- 隠しキーだけに頼らず、操作一覧と解除ボタンを用意する。初期状態は無効。
- 投影に設定フォーム・管理者情報・エラー詳細を出さず、必要時だけ小さな操作を出す。

### ルート変更案

| 用途 | 現在 | 統合後 |
| --- | --- | --- |
| 設定 | `/:roomCode/settings` | `/:roomCode/admin?tab=settings` |
| 抽選操作 | `/:roomCode/controller` | `/:roomCode/admin?tab=progress` |
| 投影 | `/:roomCode/display` | 維持、操作オーバーレイは任意追加 |
| 参加 | `/:roomCode/participant` | 維持 |
| 短縮入口 | `/:roomCode` | participantへの転送を維持 |

旧settings/controllerは対応するタブへredirectし、既存ブックマークを壊さない。
QRの参加URLは変えない。ホームの運営導線はコンソール1本にする。

### データ/API 変更案

- 統合だけならDB・RESTの追加は不要。既存設定・control APIを使う。
- 運営コンソールはdisplayモードのWSを1本だけ持つ。
- 現在のcontroller操作を共通composableへ抽出し、オーバーレイからも使う。
- 現在のPinia接続storeは単一接続を扱うため、子コンポーネントから接続・切断しない。
- コンソールの親が購読を管理し、タブ変更では接続を維持する。
- 別ウィンドウのdisplayは別接続でよい。各画面は同じサーバー状態で描画する。
- 画面の管理者チェックに加え、既存のサーバー側admin判定を必ず維持する。
- 別管理者による設定変更を反映する際は、未保存編集を黙って上書きしない。

### 実装ステップ（小さく分割）

1. Controllerの操作処理とSettingsのフォームを、それぞれ再利用可能に切り出す。
2. adminルートとタブを作り、親にWS接続の責務を集める。
3. 旧ルート転送とホームの導線を変更し、QR・直接アクセスを確認する。
4. 設定編集中はショートカットを無効化し、モーダル・入力欄の保護を維持する。
5. 必要ならdisplayへ操作オーバーレイを追加する。通常投影から明示的に有効化する。
6. 管理者以外・権限変更・全画面・通信断・別窓操作で通し確認する。

### リスク・工数感・12月の推奨

コンソール統合はM、displayへの追加は別途M。
タブのアンマウントでWSが切れる事故、設定入力中のキー誤作動、投影への操作表示がリスク。
12月はコンソール統合を推奨。オーバーレイは1台運用が必要な場合だけ追加する。
displayは遠距離の視認性、participantは個人カードとスマホ操作のため分離を維持する。

## 4. スタート／ストップの物理ボタン

### 概要・現在の状態

このブランチの `Controller.vue` にはキー入力による操作が追加されている。
Space / Enter / → / PageDown が抽選開始・確定の切替、Esc / Backspace が抽選取消、QがQR切替。
実装では ← / PageUp も同じ切替に対応している。
ここでの「ストップ」は球の確定であり、ゲーム全体の終了ではない。
waiting中のゲーム開始やゲーム終了は、画面の確認操作を使う。

- USBプレゼンター、フットスイッチ、マクロパッドが対応キーを送れば既存処理で動く。
- 入力欄・IME変換中・修飾キー・モーダル中は無視する。
- キーリピート、400ms以内の連打、通信処理中・未準備状態も抑制している。
- Controllerのあるブラウザウィンドウにフォーカスが必要。displayだけでは操作できない。
- 個々の機材が送るキーは実機確認する。PageDown送信ならそのまま使いやすい。

### ユーザー体験と選択肢

| 方式 | 体験・接続 | データ/API | 工数 | 12月 |
| --- | --- | --- | --- | --- |
| USBキー入力 | 挿してControllerを前面へ。1回押すと回転、次で確定 | 既存API | S | 第一候補 |
| WebHID | ブラウザで機器を選び、HIDレポートを操作に変換 | 既存API、機器対応層 | M | 必要時のみ |
| Web Serial | シリアル機器を選び、START/FINISH等の信号を受信 | 既存API、通信プロトコル | M | 試作枠 |
| M5Stack / ESP32 | Wi-Fi接続し、ボタンからRESTを呼ぶ | デバイス認証・専用API | L | 見送り |

WebHID / Web Serialは候補。採用前に会場PC・ブラウザで対応と許可手順を確認する。
標準キーボードとして動く機材を、WebHIDで直接読む必要はない。
ブラウザ経由ならログイン済み運営セッションを使え、機材に管理者秘密情報を持たせずに済む。

### データ/API 変更案と認証

USB方式はデータ・API変更なし。画面のボタンと同じcontrol処理に流す。
WebHID / Serialもブラウザ内で既存APIへ変換し、任意のURLを機材から指定させない。

M5Stack / ESP32から直接呼ぶ場合、現状の認証をそのまま流用しない。
OpenAPIの認証は `X-Forwarded-User` で、想定はtraQ / NeoShowcase側の認証プロキシが付与する構成。
リポジトリだけでは本番プロキシの設定は確認できないため、配備時に経路を確認する。
さらに現在の `middleware/user.go` はヘッダー欠落時に `traP` を設定する。
デバイス対応前に、このフォールバックを本番で許容しない認証境界を設計する必要がある。
マイコンが管理者名を `X-Forwarded-User` に入れる方式は、本人確認にならない。

デバイストークンを採用するなら以下を別機能として実装する。

- 管理者がログイン済み画面から、ルーム限定・期限付きのトークンを発行する。
- `device_tokens` にハッシュ・roomId・発行者・scope・期限・失効日時・最終利用を保存する。
- 平文は発行時だけ表示し、URL・ログ・配布ソースへ入れない。
- scopeはpick:start / pick:finish / pick:cancelなど必要最小限。設定変更・部屋削除は不可。
- 発行者が管理者でなくなった場合や部屋終了時も無効化し、画面から即時失効できる。
- `POST /api/device/rooms/{roomId}/commands` をBearer専用認証にする案。
- bodyはcommandId、action、expectedPickId。start/finishを明示し、曖昧なtoggleを送らない。
- commandIdの一意制約で再送を処理し、古いpickIdへの確定は409で拒否する。
- HTTPS、送信頻度制限、操作監査を実装。ヘッダー認証と混ぜずactor種別を明確にする。
- プロキシが非ブラウザのBearer要求を通せるか確認し、必要なら専用の認証経路を用意する。
- デバイス用状態取得は最小限とし、状態確認と操作の競合はexpectedPickIdで防ぐ。

### 実装ステップ（小さく分割）

1. 手持ちUSB機材の送信キーを確認し、PageDownまたはSpaceへ割り当てる。
2. 実際の進行画面で、押下・長押し・二度押し・取消・QR・フォーカス移動を試す。
3. 「抽選操作を有効化」の表示と、接続状態・picking状態を司会から見える位置に置く。
4. コンソール統合後も、進行タブでだけキーを受け、設定タブでは無効化する。
5. 本番PC・投影・音響・機材でリハーサルし、通常キーボードを予備に置く。
6. USBで満たせない要件が出たらHID/Serialを試し、直接RESTは別案件にする。

### リスク・工数感・12月の推奨

USB方式はS。フォーカス喪失、機材固有キー、電池切れ、無線干渉、連打が主なリスク。
400msの抑制は誤操作を完全には防がない。長押しと実機の送信パターンを確認する。
複数管理者や機材からの遅延要求は、将来pickIdを導入してサーバー側でも区別したい。
通信エラー時は現状どおり状態を再取得し、確定を盲目的に自動再送しない。
12月はUSBキー入力を推奨。1台投影兼用なら、管理者用display操作を先に小さく追加する。
M5Stack / ESP32の直接RESTは認証・再送・会場Wi-Fiまで含むため、本番後に回す。
